## Mobile horizontal-scroll — 3 real causes found and fixed (`047b699`, `228ec15`, `33f0c2f`)

Verified with `document.documentElement.scrollWidth` vs `clientWidth` at a 375px viewport (not assumed from a screenshot) — found `578 > 375`, fixed in three passes as each fix revealed the next layer:

1. `SiteSwitcher`'s native `<select>` had no width constraint — rendered width followed the full selected URL text. Added `max-w-[160px] truncate`.
2. Root cause, present in all three app-shell layouts (`dashboard`, `studio`, `review`): `<div className="flex-1">{children}</div>` next to `<IconRail>` — flex items default to `min-width: auto`, so `flex-1` alone never let content shrink below its intrinsic width. Added `min-w-0`.
3. Last layer: the 4-tab `TabsList` itself didn't fit its now-correctly-constrained container and had no wrap/scroll behavior. Scoped `overflow-x-auto` to this one `TabsList` instance, not the shared `ui/tabs.tsx` primitive.

Final state: `scrollWidth === clientWidth` (375 === 375) on production, confirmed via `$B js` against the live authenticated dashboard, not assumed from a single screenshot.

## SSRF / public-fetch safety hardening (`92a33e8`)

**Real, live gap found on inspection, not assumed:** `fetchHtml` (crawler.ts) and `fetchSitemapUrls` (gsc-client.ts) called raw `fetch()`/`fetchImpl()` directly — zero scheme validation, zero IP validation, no redirect re-validation, no response-size cap, no DNS-rebinding defense, no credential-URL rejection. A "website URL" of `http://169.254.169.254/` (cloud metadata) or `http://localhost/` would have been fetched for real, right now, in production. Sitemap `<loc>` entries also weren't hostname-filtered before re-entering the crawl queue — a malicious sitemap.xml could inject arbitrary off-site targets.

**`src/lib/safe-fetch.ts`:** shared `safeFetch`, defense in depth — rejects non-http(s) schemes and embedded credentials before any network call; resolves DNS itself via `dns.lookup` and rejects if ANY resolved address (checked for both IPv4 and IPv6, including IPv4-mapped/NAT64 forms) is private/loopback/link-local/reserved/cloud-metadata; pins the actual TCP connection to that pre-validated address via undici's dispatcher `lookup` override (closes the DNS-rebinding window between check and connect — the attacker's nameserver can't swap the answer between the two, because the client never asks again); never auto-follows redirects, each hop is re-validated from scratch up to a bounded count; caps response bytes read independent of a spoofable `Content-Length`. `undici` (previously only a transitive dependency via `cheerio`) is now pinned as a direct dependency at the already-resolved 7.29.0.

`crawler.ts`'s `fetchHtml`/`fetchPageMeta` and `gsc-client.ts`'s `fetchSitemapUrls` now default to this for all real traffic; existing tests are unaffected since they already inject their own `fetchImpl` mock, bypassing the default entirely. `fetchSitemapUrls` also now drops any `<loc>` entry whose hostname doesn't match the audited site.

## Critical hotfix — safeFetch was silently breaking every real crawl (`50accf0`)

**Found by live testing, not by any unit test — exactly why the directive insists on it.** After deploying the SSRF hardening (`92a33e8`) and the GEO Specialist (`4b241b6`), ran a live verification scan against production for the real YOKI site and got `pagesScanned: 0, findingsCreated: 0` — a silent failure, not a crash, because `fetchHtml`'s existing try/catch (by design, so one page's failure doesn't abort the scan loop over the rest) swallowed it.

## Phase 1F, final automatically-draftable row — internal_link_fix (2026-09-28, commit `f4df8b1`, deployed `dpl_6TVQyzBTuTNLVXUp2C96iCGCBBh1`)

## Phase 1C — architecture decision accepted, implementation not started (2026-09-29, commit `3383d1d`, design only)

**Selected architecture:** extend the existing Postgres + QStash pattern (Phase 1B's precedent) — no new external service, no new credentials. New `GenerationJob` table (mirrors `ScanJob`'s proven shape; kept separate from `Action` since `Action` is a post-generation decision artifact with its own approve/reject/edit lifecycle, not a pre-generation queue slot) plus a new `ProviderCircuitBreaker` table keyed by `(provider, model)`, not per-tenant (a provider outage is a shared external fact — per-tenant scoping would be worse isolation, not better). Same dual-auth sweep pattern (`CRON_SECRET` bearer OR QStash signature) and atomic-claim pattern (`updateMany({where: {status: 'queued'}}})`) `/api/scan/process`/`claimAndRunScanJob` already use, extended to a new `/api/generation/process` endpoint. Full design, state machine, idempotency strategy, and circuit-breaker thresholds (justified from real volume — none existed anywhere to recover) in `docs/superpowers/specs/2026-09-28-phase1c-generation-queue-adr.md`.

**Scope confirmed by the account owner 2026-09-29** (the one real product decision this ADR surfaced, per the directive's own rule to stop for exactly this before implementing): covers `run-scan.ts`'s 6 actionTypes (`meta_description`, `canonical_fix`, `structured_data_fix`, `entity_markup_fix`, `restricted_wording_fix`, `internal_link_fix`) plus `retry-draft`'s manual retry — all already background (inside a ScanJob) or an explicit "try again" action, so queueing them needs zero UX redesign. **Explicitly out of scope, named not hidden:** `content-studio/draft-generator.ts` (synchronous, customer actively watching the Studio page — converting it to enqueue-then-poll is a real frontend redesign, not a backend reliability change), `dashboard-insight.ts` (already has a real fallback, no visible failure state to fix), `feedback-analysis.ts`/`preference-candidates.ts` (low-volume, on-demand, no reported reliability problem).
